# LLM 驱动动态难度调整（DDA）可行性验证报告

## 一、实验背景与目标

UE5 RPG 战斗原型目前采用基于死亡次数的规则 DDA：玩家连续死亡越多，难度降得越多。这套方案实现简单、响应快、成本为零，但只能看一个维度。玩家为什么死、差在哪里、是不是已经接近通关，它都判断不了。

本实验在现有规则 DDA 基础上引入 LLM，使其读取多维玩家行为画像并同时对多个难度参数给出调整建议，并与固定难度、死亡次数规则 DDA 三组进行对照，验证 LLM 驱动的多因素 DDA 策略是否能够在主观体验和玩家状态适配方面体现相较于单参数规则 DDA 的额外价值。

实验要回答四个问题：

1. LLM 驱动的多因素 DDA 方案是否有额外价值
2. 价值出现在哪些场景
3. 代价是什么
4. 最终应该如何使用

## 二、实验设计

### 2.1 三组设计

实验设置三组对照：

| 组别 | 难度调整方式                                  | 作用                |
| :--- | :-------------------------------------------- | :------------ |
| A    | 固定难度，三个参数恒为 1.0                    | 基准组              |
| B    | 按死亡次数查表调难度系数，CD 和前摇不调       | 传统方法基准        |
| C    | LLM 读取玩家画像后给建议，失败时回退 B 组规则 | 验证 LLM 的额外价值 |

三组共用同一套战斗逻辑，只在难度决策层分流。组别通过控制台命令 `DDA.SetGroup 0/1/2` 切换。

C 组的数据流是：

```
玩家战斗 → 行为埋点 → 结构化画像 + 标签 → LLM → JSON 决策 → UE 校验 → 参数调整
```

LLM 不直接控制游戏，只输出建议。所有建议必须经过 UE 侧校验层，异常时回退规则 DDA。

### 2.2 实验判定标准

本报告在实验前预设的判定标准：

| 结论 | 判定条件                            |
| :--- | :---------------------------------- |
| A    | C 组主观评分均值比 B 组高 ≥ 0.5 分  |
| B    | C 组比 B 组高 0.3–0.5 分            |
| C    | C 组比 B 组高 < 0.3 分              |
| D    | 参数越界率 > 20% 或解析失败率 > 20% |

延迟硬线：模式 B 下 P95 > 10s 判定不可接受。

## 三、玩家画像与数据采集

埋点最终保留五个维度：

| 字段             | 含义         |
| :--------------- | :----------- |
| deathCount       | 死亡次数     |
| avgSurvivalTime  | 平均存活时间 |
| dashFrequency    | 闪避频率     |
| perfectDodgeRate | 完美闪避率   |
| skillFrequency   | 技能释放频率 |

另外保留死亡时 Boss 血量作为辅助信息，用于判断玩家是否接近通关。

原计划还包括闪避成功率和连招段数两个维度，但前者需要判定闪避后的短窗口是否受击，实现成本高；后者在原型里不产生连招中断场景，数据没有意义。两者都在实施阶段砍掉。

每局结束由 C++ 计算派生指标、更新最近三局趋势、生成标签，组装成 JSON 发给 LLM。

## 四、LLM 链路与安全机制

### 4.1 调用方式

LLM 采用 DeepSeek 云端 API，模型 `deepseek-flash`（对应 DeepSeek-V4.1-Flash）。调用时机是模式 B（战局结束后调整）：每局结束发请求，下一局用上。

选模式 B 的原因是延迟。实测连接复用下 P95 延迟 5.8 秒，UE 端新建连接含 TLS 握手时单次可达约 10 秒。实时调用会打断战斗节奏。

### 4.2 UE 侧校验与回退

LLM 返回结果经过四步校验：

1. JSON 可解析
2. 必要字段齐全、类型正确
3. 数值在允许范围内
4. 单次变化幅度不超限

其中第 3、4 步异常时采用裁剪策略，第 1、2 步失败则直接回退规则 DDA。

数值范围：difficultyMultiplier 在 [0.6, 1.2]，另两项在 [0.8, 1.2]。单次幅度：difficultyMultiplier 变化不超过 0.15，另两项不超过 0.10。

原计划中的“decision 与参数方向一致性检查”尚未实现，本次实验未将其作为已完成的安全机制，作为后续完善项记录。

Prompt 里写入同样的数值范围和幅度约束。G2 测试阶段曾通过 Prompt 注入尝试诱导模型输出超范围的 difficultyMultiplier=5.0，但模型仍返回 0.85，未接受该诱导。该结果说明当前 Prompt 约束在该测试样例下有效，但不能替代 UE 侧的范围校验，因此最终仍以代码校验为准。

## 五、预测试与门禁

为避免直接进入 A/B/C 实验后才发现数据、LLM 链路或输出稳定性存在问题，实验前设置 G1～G3 三道门禁，分别验证数据采集正确性、系统容错能力和模型输出一致性。

### 5.1 G1 数据准确性

人工打一局，故意死两次，核对死亡次数、存活时间、死亡时 Boss 血量。手动触发闪避与完美闪避，核对比率。重开后确认该清零的清零、该保留的保留。全部通过。

过程中修了两处问题：

- 完美闪避率异常，原因 `RecordPerfectDodge` 里多记了一次总闪避数，导致分母偏大
- 闪避频率一直为 0，原因是派生计算用的还是废弃的 DashCount 字段

### 5.2 G2 系统容错

五条测试全过：

1. 正常画像输入 → 输出合法 JSON 且参数生效
2. LLM 服务不可用 → 超时回退，游戏不中断
3. 输出非法 JSON → 回退
4. 输出超范围数值 → 裁剪生效
5. 输出幅度过大 → 幅度限制生效

其中第 2、3 条在调试期间自然触发过，游戏全程正常运行。第 4、5 条用代码注入方式验证。

### 5.3 G3 输出一致性

固定三份代表性画像，各调用 LLM 5 次。

三份画像分别是：闪避强输出弱、综合强、综合弱。

结果：

| 画像         | decision 方向一致率 | 参数极差                     |
| :----------- | :------------------ | :--------------------------- |
| 闪避强输出弱 | 5/5 down            | Diff 0.05，CD 0.05，Windup 0 |
| 综合强       | 5/5 up              | Diff 0，CD 0.05，Windup 0.05 |
| 综合弱       | 5/5 down            | 全 0                         |

三份画像全部满足本阶段预设的一致性门槛。该结果说明 LLM 在当前测试画像下的输出稳定，但不能替代大规模一致性验证。

## 六、三组对照实验

### 6.1 实验条件

分三次 PIE 完成，每次 PIE 内跑一组：

- 第 1 次 PIE：`DDA.SetGroup 0`，打 3 局
- 第 2 次 PIE：`DDA.SetGroup 1`，打 3 局
- 第 3 次 PIE：`DDA.SetGroup 2`，打 3 局

每次 PIE 内每局打死后点“再来一局”，GameInstance 在本次 PIE 内保留，CSV 追加。切换到下一组时重启 PIE。

### 6.2 主观评分结果

| 指标           | A     | B     | C     |
| :------------- | :---- | :---- | :---- |
| 主观评分均值   | 2.33  | 2.00  | 3.00  |
| 平均死亡次数   | 1.0   | 1.33  | 3.33  |
| 平均存活时间   | 35.10 | 15.46 | 28.74 |
| 平均闪避频率   | 18.98 | 6.27  | 8.75  |
| 平均完美闪避率 | 0.71  | 0.75  | 0.81  |

C 组评分均值比 B 组高 1.0 分，超过本报告第 2.2 节的预设阈值。

B 组三局评分完全一致，都是 2 分。规则 DDA 的调整稳定但缺乏变化，只能按死亡次数降难度，玩家感受不到“这局调得刚刚好”。C 组评分 2/4/3，波动大但均值高，LLM 有时判断一般，有时判断很好。

C 组三局明细：

| C 组     | 评分 | 说明                                         |
| :------- | :--- | :------------------------------------------- |
| 第 1 局  | 2    | 使用规则回退（模式 B 首局无上一局 LLM 结果） |
| 第 2 局  | 4    | LLM 生效                                     |
| 第 3 局  | 3    | LLM 生效                                     |
| C 组整体 | 3.00 | —                                            |

由于模式 B 的时序特性，C 组首局使用规则回退，因此 C 组 3 局均值代表完整 C 组方案的整体体验，不应直接视为 LLM 单独作用下的平均评分。

### 6.3 工程指标

| 指标                 | 值                   |
| :------------------- | :------------------- |
| 平均延迟（连接复用） | 3.9 s                |
| P50                  | 3.9 s                |
| P95                  | 5.8 s                |
| 平均总 Token         | 2725                 |
| 单次成本             | 0.014 元             |
| 总成本               | 0.49 元（34 次调用） |
| C 组首局回退         | 1/3（模式 B 时序）   |
| C 组解析成功         | 2/2 = 100%           |

P50 是中位数延迟，P95 表示 95% 的请求延迟不超过该值，即约 5% 的请求延迟高于该值。P95 5.8 秒低于方案设定的 10 秒硬线。

UE 端新建连接时还会额外产生 TLS 握手开销，实际测试中单次请求可达到约 10 秒；连接复用情况下，PowerShell 测得 P95 为 5.8 秒。模式 B 下这个延迟不影响战斗体验，因为请求发出去后玩家还在胜利界面，下一局才用到结果。

## 七、结果分析

### 7.1 LLM 的额外价值

本次实验观察到的核心差异并非“LLM 能够简单地判断升难度或降难度”，而是能够根据不同能力维度之间的组合关系，对不同难度参数采取不同方向和幅度的调整。

G3 阶段观察到三种画像触发了三种不同调法：

| 玩家画像       | LLM 判断 | Difficulty | CD   | Windup | 调整意图         |
| :------------- | :------- | :--------- | :--- | :----- | :--------------- |
| 闪避强、输出弱 | Down     | ↓          | ↑    | =      | 增加输出窗口     |
| 综合强         | Up       | ↑          | ↓    | ↓      | 提高挑战         |
| 综合弱         | Down     | ↓          | ↑    | ↑      | 全面降低战斗压力 |

例如“闪避强、输出弱”和“综合弱”虽然都被判断为降难度，但前者主要通过增加输出窗口改善玩家机会，后者则同时降低技能冷却压力和攻击前摇压力。二者体现的是不同的困难来源。

规则引擎只看死亡次数，遇到这两种情况都会把所有参数一起降，无法区分困难类型。这是 LLM 方案相比规则 DDA 的核心差异。

### 7.2 延迟与成本

延迟：UE 端新建连接含 TLS 约 10 秒，连接复用下 P95 为 5.8 秒。仅适合战局后调整，不适合实时。
成本：平均每次调用约 2725 Token，单次 1.4 分钱，总成本 0.49 元。

### 7.3 最终应该如何使用

规则引擎作为确定性的安全兜底，负责最终参数控制；LLM 负责低频、多因素的玩家状态评估与策略建议。

LLM 不进入实时链路，而是在战局结束后作为策略分析器，给下一局提供调整方向。这个定位既保留了 LLM 的多因素判断能力，又避免了延迟和成本带来的风险。

## 八、结论

根据第 2.2 节的预承诺判定标准，C 组主观评分均值比 B 组高 1.00 分，达到结论 A 的阈值。该结论的适用条件为：单人 9 局、固定组别顺序、B/C 参数空间不同。在此条件下，LLM 驱动的多因素 DDA 方案表现出正向体验信号。

但本实验并不能证明 LLM 决策器在同等参数空间下统计显著优于规则决策器。本实验所能支持的最强结论是：LLM 在区分不同困难类型并分配不同参数调整方向方面，表现出可观察的额外价值。

## 九、局限与后续方向

### 9.1 样本规模与组别顺序

本次实验为单人自我测试，每组 3 局，共 9 局。这个规模够看趋势、够验证工程链路，但不够做统计推断。

组别按 A → B → C 固定顺序执行，没做随机化。顺序固定便于流程控制，但会引入熟练度和疲劳干扰。后续如果扩大样本，会改成拉丁方顺序，并把样本扩到多人多局。

另外，Trend 判断只能在单次 PIE 内的 3 局之间进行，无法跨 PIE 累积。本次实验中三组内部都没有触发 `improving` 标签。

### 9.2 B/C 参数空间差异

B 组只调难度系数，C 组同时调难度系数、技能冷却和攻击前摇。

这个差异是有意设计的。B 组代表现有的死亡次数规则，C 组代表 LLM 驱动的多因素方案，对比的是两套方案的整体效果，不是两个决策器的能力。如果之后想单独验证 LLM 的决策能力，会加一组“规则驱动的多参数 DDA”做对照。

### 9.3 画像维度

画像最终保留五个维度。原计划里的闪避成功率和连招段数，前者判定窗口实现成本高，后者在原型里不产生连招中断场景，都在实施阶段砍掉。

这两个维度的缺失会限制 LLM 的判断空间。等原型支持这两种行为之后，会补回来。

### 9.4 延迟与调用时机

这次用的是云端 API，UE 端新建连接含 TLS 握手时单次可达约 10 秒。这个延迟决定了 LLM 只能做战局后调整，不能进实时链路。如果后面改用长连接或本地模型，延迟能压下来，但本地模型能力有限，需要权衡。

### 9.5 主观评分方式

主观评分是实验后凭记忆填的，精度有限。后续会每局结束立即评分，并增加评分维度。

### 9.6 未实现项

安全层第 5 步（decision 与参数方向一致性检查）没实现。原计划里把它列为可选完善项，本次实验也没遇到方向矛盾的实际案例，所以没有补。
