# LLM + DDA DevLog

> UE5 游戏 DDA 实验开发与验证记录
> 以 RPG 战斗原型为实验载体，引入 LLM 参与动态难度调整决策。通过三组对照实验，验证 LLM 是否能利用多维玩家行为数据做出比传统规则更合理的难度调整，并探索其延迟、稳定性与成本边界。

## Day 1（2026.09.22）

### 今日完成

启动 LLM + DDA 实验，完成了模型初步验证和游戏内数据采集系统的起步搭建。

#### 一、LLM 模型验证

- 原计划用本地模型，但安装包下载太慢，改为接入 DeepSeek 云端 API
- 手动构造一份玩家画像（闪避强、输出弱），连续发给模型 5 次，让它判断该不该调难度、怎么调
- 5 次里，模型都给出了方向一致的判断：应该降低难度，并延长 Boss 技能冷却，而不是去改攻击前摇
- 解决了 PowerShell 中文显示乱码的问题，确认模型返回的数据能被正常解析

5 次测试结果：

| 次数 | 模型判断 | 难度系数调整 | 技能冷却调整 | 攻击前摇调整 |
| :--- | :------- | :----------- | :----------- | :----------- |
| 1    | 降低难度 | 降到 0.85    | 延长到 1.1   | 不变         |
| 2    | 降低难度 | 降到 0.85    | 延长到 1.1   | 不变         |
| 3    | 降低难度 | 降到 0.9     | 延长到 1.1   | 不变         |
| 4    | 降低难度 | 降到 0.85    | 延长到 1.1   | 不变         |
| 5    | 降低难度 | 降到 0.85    | 延长到 1.15  | 不变         |

> 表格说明：难度系数越低游戏越简单；技能冷却越长，Boss 放技能越慢；攻击前摇不变，说明模型判断玩家不需要更多反应时间。

#### 二、游戏内数据采集系统

- 在 C++ 里定义了一个玩家数据结构，用来记录死亡次数、存活时间、Dash 使用、完美闪避、连招、技能使用等行为
- 写了一个游戏实例类，提供一组可以被蓝图调用的记录函数
- 把现有的蓝图 GameInstance 重设父类为这个 C++ 类，让蓝图可以直接调用新函数
- 在玩家死亡事件上挂了记录节点，测试通过：故意死几次，死亡次数会正确递增
- 把 Boss 当前血量百分比接入记录系统，让每次死亡时记录的数据是真实值而不是占位符
- 过程中解决了几个编译问题：UE 5.7 的日志宏在特定情况下会导致编译器崩溃，后来改用屏幕输出代替；中文文本复制粘贴时容易带隐藏字符，后来全部改英文

### 今日思考

今天让模型第一次真正参与游戏决策。虽然只是用假数据做测试，但结果比预期好。

最直接的感受是，模型确实在做判断，而不是套公式。我给的这份画像是“闪避强、输出弱”，如果只看死亡次数，规则引擎会直接降难度。但模型 5 次里都识别出“闪避不是问题，输出才是”，所以没有去动攻击前摇，而是降难度系数、拉长 Boss 技能间隔，给玩家更多输出窗口。这至少说明，在这个人为构造的“闪避强、输出弱”场景下，LLM 能够根据多维画像区分玩家的闪避能力与输出能力，而不是仅依据死亡次数做统一降难。这是一个值得后续验证的实验现象，不是最终结论。

另外，本次 5 次重复调用中，4 次给出了完全相同的参数，另 1 次仅在难度系数和技能冷却参数上出现小幅变化，初步表现出较好的重复调用一致性。后续仍需按正式的一致性测试流程进行验证。

埋点部分比预想的顺利。原以为在蓝图和 C++ 之间搭桥要花不少时间，但重设父类、修改之前的属性集的 C++ 文件后，蓝图里直接就能搜到新函数和直接获得属性值，挂上死亡事件跑一局就通了。目前已经能看到死亡次数正确递增，Boss 血量也能读到真实值。

今天踩了不少坑，主要都是 UE 5.7 的编译器问题，而不是逻辑问题。解决的思路都是“绕过它，而不是硬刚”——日志宏会崩就用屏幕输出代替，中文会乱码就全改英文。

## Day 2（2026.09.23）

### 今日完成

#### 一、数据采集准确性验证

昨天搭好的数据采集骨架，今天逐项验证：

+ 死亡次数统计准确
+ 平均存活时间合理
+ 闪避频率有值
+ 完美闪避率正确
+ 技能释放频率有值
+ 跨局数据保留正常

跨局保留通过连续打多局验证：第 1 局 RecentDodgeRates 长度是 1，第 2 局变 2，第 3 局变 3，第 4 局开始挤掉最老的，长度固定在 3。

过程中修复了两个计数问题：

+ 完美闪避率异常，是因为 RecordPerfectDodge 多记了一次总闪避数，导致分母偏大。删掉后比率正常
+ 闪避频率为 0，是因为 DashFrequency 算的还是废弃的 DashCount，改成用 DodgeTotalCount 后正常

同时把不再使用的字段和函数清理掉，保留了五个核心维度：死亡次数、平均存活时间、闪避频率、完美闪避率、技能释放频率。

#### 二、JSON 组装 + LLM 链路接入

JSON 组装：新增 BuildProfileJson()，把玩家数据转成结构化 JSON。输出格式和方案设计一致，包含基础字段、标签数组、趋势、当前参数。跑一局后能在 Saved/ProfileJson.txt 里看到完整 JSON。

LLM 链路：新增三个函数完成完整链路——

+ RequestLLMDecision()：读环境变量里的 API Key，拼 Prompt，构造请求体，发给 DeepSeek
+ OnLLMResponseReceived()：收到响应后交给校验层处理
+ ValidateAndParseLLMResponse()：解析响应、抠出决策 JSON、检查字段、裁剪数值范围

链路跑通后，屏幕上会出现 LLM 返回的三个难度参数。

### 今日思考

今天最大的收获是完整走通了一条从游戏内数据到 LLM 决策的链路。

一开始担心 C++ 和 HTTP 集成会很复杂，实际写下来结构很清晰：数据 → JSON → 请求 → 响应 → 校验 → 参数。每一层职责单一，出问题也好定位。

链路调试中踩了几个坑，都是环境问题而不是业务逻辑问题：

+ TLS 握手超时。我设置的超时是 10 秒，连接 DeepSeek 时 TLS 握手走不完就断了。改成 30 秒就稳定了。
+ 代理冲突。开着梯子的时候 UE 的 HTTP 请求走不通，或者响应被中途截断。关掉梯子直连反而稳定。
+ SSL 模块依赖。Build.cs 里需要显式加 SSL 和 Sockets 模块，否则 HTTPS 请求发不出去

这些问题本身不属于核心业务逻辑，但任何一个环节出问题都会导致整条 LLM 链路无法正常工作。解决方式都一样：看日志、缩小范围、逐个排除。

LLM 返回的结果值得记录一下。我给的画像是一个“闪避好、技能积极、输出强”的玩家，LLM 判断结果为 Diff=1.05，表现为轻微提高难度。与当前仅依据死亡次数的规则 DDA 相比，这次结果体现出 LLM 能够同时参考闪避、技能使用和输出表现进行调整。

不过这个结论现在只能算一个观察，不能算验证。因为参数还没真正作用到游戏里，三组对照实验也还没跑。完整结论要等后续实验跑完才能定。

过程中发现一个小遗留问题：Saved/ProfileJson.txt 文件没有随每局战斗刷新，因为之前重构时把写文件的代码一起清理掉了。目前 JSON 只在内存里生成、发送，没落盘。下次要在 RequestLLMDecision 里补上写文件的逻辑，方便调试和存档。

接下来要把 LLM 返回的三个参数真正应用到游戏：

+ 难度系数接入伤害计算链路
+ 技能冷却接入 Boss 技能 CD
+ 攻击前摇接入 Boss 攻击动画

#### 七、工程指标

延迟是用 PowerShell 连续调 10 次 DeepSeek API 测出来的。P50 是中位数延迟；P95 表示 95% 的请求延迟不超过该值，剩余约 5% 的请求延迟高于该值。

| 指标                      | 值                         |
| :------------------------ | :------------------------- |
| 平均延迟（连接复用）      | 3.9 s                      |
| P50（中位数延迟）         | 3.9 s                      |
| P95（95% 请求的延迟上限） | 5.8 s                      |
| 单次 Token                | 2725                       |
| 单次成本                  | 0.014 元                   |
| 总成本                    | 0.49 元（34 次调用）       |
| 一致性                    | 3 份画像 × 5 次全过        |
| 首局回退                  | 1/3（C 组第 1 局时序原因） |

P95 = 5.8 秒，低于方案的延迟硬线 10 秒。UE 客户端每次调用含 TLS 握手，实际延迟约 10 秒。模式 B 战局后调整，这个延迟不影响战斗体验。

### 今日思考

今天算是实验主体收尾的一天，三组数据第一次跑出来，和预期方向一致。

C 组评分均值 3.0，比 B 组高 1.0 分。B 组三局评分完全一致（都是 2 分），说明规则 DDA 的调整稳定但缺乏变化——它只能按死亡次数降难度，玩家感受不到“这局调得刚刚好”。C 组评分 2/4/3，波动大但均值高，LLM 有时判断一般，有时判断很好。

这和 G3 阶段的观察一致。LLM 能区分“闪避强输出弱”和“综合弱”两种困难类型，调法不同：前者降难度但不动前摇，后者降难度同时拉长 CD 和前摇。规则只看死亡次数，把所有参数一起降，无法区分。

成本量级也值得记一下。单次 1.4 分钱，换来比规则 DDA 高 1 分的体验评分。这个权衡在低频调整（模式 B）下成立，实时高频调用的成本会放大几十倍，这也是为什么最终方案把 LLM 定位在战局后调整而不是实时。

本次实验为单人样本，共 9 局数据，且组别顺序固定（A → B → C），存在熟练度变化、疲劳、顺序效应等潜在干扰因素，只能看趋势，不能下统计结论。三组均值差异在报告里作为观察结果呈现，不作为统计推断依据。

另外，由于分三次 PIE 完成，每次 PIE 使用新的 GameInstance，Trend 判断只能在单次 PIE 内的 3 局之间进行，无法跨 PIE 累积。本次实验中，A/B/C 三组各自内部 3 局的完美闪避率没有呈现第 3 局比第 1 局提升 0.05 以上的趋势，因此 improving 标签未触发。
